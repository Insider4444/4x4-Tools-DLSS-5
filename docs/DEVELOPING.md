# Develop, test and publish

Keep one public source repository. `src/` contains the plug-in; `installer/`, `scripts/` and tests contain its build and release tools. Public Releases have exactly three assets: the installer EXE, a manual-install ZIP and SHA256SUMS.txt. The ZIP contains only `4x4Tools-DLSS5/` with installed files and `README.txt`.

Adobe/NVIDIA development SDKs are kept in the owner's separate **private** build-dependency repository. The release workflow reads a pinned dependency commit with a read-only SSH deploy key in the `SDK_DEPLOY_KEY` Actions secret. No personal GitHub token is stored in the workflow. The runtime is downloaded from the existing public v1.0 package and checked against its pinned SHA-256. GitHub's standard source archive links are generated by GitHub; they are not installation packages.

## Move to another PC

Extract your private developer kit and open PowerShell in `4x4Tools-DLSS5-developer`.

Install Windows x64, Git, Visual Studio 2022/2026 Build Tools with Desktop development with C++, CMake tools and a Windows SDK. Adobe applications and a compatible NVIDIA GPU/driver are needed for full local testing. The kit includes local Adobe/NVIDIA SDKs, runtime and NSIS; it does not include the Microsoft compiler or Adobe applications.

```powershell
.\setup-dev.ps1
gh auth login
git pull --ff-only origin main
```

GitHub CLI authentication is only needed for GitHub operations. `setup-dev.ps1` restores public Git history from `repository.bundle` without overwriting extracted working files. All bundled dependency paths are relative. Your account, credentials, local install receipts, footage and projects are not carried inside the kit. If Git reports divergent changes after pulling, integrate those changes normally before proceeding; never reset away work you want to retain.

For a normal source checkout without the kit, run setup with your own SDK/runtime/NSIS paths as described in BUILDING.md.

## Local development loop

1. Edit code and save your projects. Fully close AE and Premiere.
2. Run `.\debug-install.ps1`. It detects source changes, incrementally builds Release, runs all tests including actual NVIDIA rendering, checks package hashes and safely replaces the shared Adobe plug-in. Windows may ask for administrator access. Backups are in `C:\ProgramData\4x4-Tools\DLSS-5\Backups`.
3. Open Adobe and test your footage. The local installation receipt proves which source was installed; it does not certify that you visually reviewed the footage. `-BuildOnly` builds and tests without installing or creating a local-install receipt.

The script uses an optimized Release build so local testing has normal performance. It refuses to replace the plug-in while Adobe is running and never force-closes an application.

## GitHub builds the release

Set `version` in `release-config.json` (for example `1.2.0`) and write release notes in `update-note.md`. Use three numeric version components and a version newer than the published release. Public file/installer versions come from this field. `resources/version-state.json` keeps Adobe's internal compatibility counter monotonic; do not edit it manually or reuse a published version. Original parameter IDs/types must stay stable.

After local installation and Adobe testing:

```powershell
.\deploy-main.ps1
```

This command audits the public file set, shows changes and notes, commits them to `main`, pushes normally and triggers `.github/workflows/release.yml`. **GitHub builds the final EXE and ZIP from that exact commit. The script does not upload locally built release binaries.** The Action runs CPU controls, Adobe host-contract and update-helper tests, verifies package contents/hashes, stages a draft release, checks server asset digests and publishes only after those checks pass. Actions runs are serialized. The script refuses source changed since the local debug installation; editing only the version or release notes is allowed.

Hosted GitHub runners have no NVIDIA GPU. Their tests do not replace local neural rendering and Adobe footage testing. Each installer's GPU preflight still runs on the end user's PC before replacing their installation.

```powershell
# Override the version and read an alternate Markdown notes file:
.\deploy-main.ps1 -Version 1.2.0 -NotesFile .\notes\v1.2.md -Wait

# Compile on GitHub and keep installable Action artifacts, without publishing:
.\deploy-main.ps1 -BuildOnly -Wait
```

`-BuildOnly` still commits/pushes and triggers GitHub; it skips the local-install requirement and leaves stable Releases unchanged. `-Wait` watches completion and returns failure when the Action fails. Without it, the script returns the run link and records it in `.local/last-deployment.json`.

The compatibility entry point `.\publish-release.ps1 -Publish` calls `deploy-main.ps1`. Without `-Publish`, it builds a local candidate and tests the compiled installer without uploading anything. Use it for installer development.

GitHub CLI needs repository access and the `workflow` OAuth scope to push workflow changes. If GitHub rejects a workflow push, run `gh auth refresh -h github.com -s workflow` and authorize the browser prompt. This does not require sharing a token with the developer kit. A failed build remains an Action failure; a failed asset upload remains a draft and is not advertised as an update. Re-run a failed workflow for the same commit to recover its draft. Published versions are never overwritten by these scripts. Fix source and retest before using a new version.

The first update-aware candidate is 1.1.0. It stays local/unpublished until the owner chooses to deploy it. Older v1.0 installations need one upgrade before the subtle update notice can work.

## Refresh the private kit

```powershell
.\scripts\developer-kit.ps1
```

The output path is printed and recorded in `.local/developer-kit-result.json`. The ZIP includes all public source/dotfiles, public Git history and your local SDK/runtime/NSIS dependencies. Do not upload this private archive. `.gitignore` excludes dependencies, `.local`, bundles and build artifacts; publishing also rejects tracked private/binary/credential files. Never force-add these files. The kit does not contain the Actions SSH deploy key; GitHub already holds it, so a different development PC only needs your CLI login.

For a deliberate SDK/runtime change, validate its license/provenance and GPU behavior, update the private dependency repository and pinned workflow commit/runtime hash, then retest. The workflow does not silently substitute an unknown model.
